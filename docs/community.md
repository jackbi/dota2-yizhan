# 社区帖：镜像到哪一步、剩下的怎么翻

`/community/nga/<tid>` 与 `/community/hupu/<pid>` 是 NGA 与虎扑的帖子镜像。首屏是**构建期渲染的
静态快照**，后面的回复由读者点「加载更多」按页取——**按的是上游自己的分页**，不是我们自己攒一批。

## 两个源的分页契约（实测）

| | 第 1 页 | 第 N 页 | 每页 | 元信息 |
| --- | --- | --- | --- | --- |
| NGA | `read.php?tid=<tid>&__output=11` | 同址加 `&page=<n>`（1 起） | 20 层 | `__PAGE` / `__ROWS`（总楼层，含主楼 0 层）/ `__R__ROWS_PAGE` |
| 虎扑 | `/<pid>.html` | `/<pid>-<n>.html`（`n` 从 2 起） | 20 条 | `__NEXT_DATA__.detail.replies`：`{count, size, current, total}`，**页码 1 起** |

虎扑踩过的两个坑：`?page=2` 返回的仍是第一页（Next.js 那层不吃这个参数），而 `replies.baseUrl`
给的 `/<pid>_0.html` 是一页空壳。真正的分页链接写在渲染出来的 DOM 里（`642044480-2.html` 这种
相对形式），照着它拼才对。这两条都钉在 `scripts/communityFloors.check.ts` 里。

## 为什么首屏只预渲染第一页

详情页是预渲染的（`getStaticPaths` + 构建期抓取），理由与其它内容页一样：爬虫与无 JS 的访客拿到的
必须是完整可读的 HTML，而构建期把榜上每个帖子的每一页都抓一遍，等于把上游请求量乘以页数
——NGA 热帖榜一轮就有几十个帖子，几百层的帖子不少见。

所以分工是：

- **首屏（静态）**：主楼 + 热评 + 第一页楼层全部摆出来（虎扑 20 条、NGA 19 层）。这些进 sitemap、能被收录；
- **点击之后（运行时）**：`/api/community/floors?source=nga|hupu&id=…&page=N` 取下一页，
  按 `data-pid` 去重后追加。**爬虫不会跟到这里**——它不是链接，且该接口带 `X-Robots-Tag: noindex`。

「还剩多少、下一跳第几页」只有一处算术（`src/lib/communityFloors.ts` 的 `floorProgress`）。
两个源的 `total` 口径不同——NGA 数的是楼层（含主楼），虎扑数的是回复——但 `page × perPage`
对两边都成立，NGA 的主楼正好补上它多算的那一条，所以一条公式够用。

## 缓存与限速

- 同一页 10 分钟内只打一次上游（`ssrCache` 的**每实例**内存缓存，键 `community-floors:<源>:<id>:<页>`）；
- 缓存里放的是**解析结果**，不是拼好的 HTML：HTML 里带着「今天 / 昨天 / 09.12」这种相对时间，
  跟缓存冻在一起的话，跨过零点的那一页就会说错日子；
- 走 `ssrCache.pace` 的 120ms 串行间隔，同一实例内的请求不会挤在一起；
- 页码上限 `MAX_FLOOR_PAGE = 40`，`id` 只收数字帖子号，地址只有两个固定模板——
  这条接口不能变成「拿任意地址来刷」的通用代理。

## 失败了怎么办

上游挂了、页码超了、正文里的非法转义让整段 JSON 解析失败——一律回 `{ ok: false, reason }`，
页面上把原因写在按钮下面，旁边始终有「前往原帖」那条出口。**任何情况下都不会把页面变成空白**：
按钮是渐进增强，关掉 JS 也能读到首屏那一页。

## 已知的取舍

- **NGA 对未登录访问打码昵称**，站内只能从引用文本里反推，反推不到的楼层没有昵称（一直如此）；
- 虎扑的 `lights` 可能来自任意一页，所以「还有 N 层」是个**上限**：点完最后一页时可能有一两条
  早就以亮评的身份出现在页面上（重复的内容不会真的插两遍，只是计数偏乐观）；
- 「加载更多」解决的是**读者能看到多少**，不是收录：帖子滑出热帖榜之后详情页仍会从产物里消失，
  这件事见 `docs/seo.md` 的「未找到 (404)」一节——那要先定「镜像页是资产还是快照」。
