# 对局复盘与地图回放

`/replay/<Valve 比赛 id>`：一局打完之后，先回答「这局怎么走成这样的」，再给一张能拖着看的小地图。
入口在赛事对阵页每一局的「复盘与回放」，以及个人战绩页的对局详情。

## 两条数据通道

复盘面板与地图回放**故意分成两次查询**，因为它们的体积差两个数量级、覆盖率也不一样：

| | 查询字段 | 上游体积 / 耗时 | 覆盖范围 |
| --- | --- | --- | --- |
| 复盘面板 | 经济与经验差、逐分钟击杀、胜率模型、塔况位掩码、推塔事件、分路结果、选手行、眼位事件 | 约 25KB / 1.4s | 所有被 STRATZ 解析的对局（含一周前的职业局） |
| 地图回放 | `playbackData`：逐秒位置、眼位坐标、肉山、建筑倒塌 | 约 400KB / 2.6s | 只有 STRATZ 下载过录像的对局 |

面板那份跟着页面一起在服务端渲染（无 JS 也能看），地图那份等读者点了「载入英雄轨迹」再取
`/api/replay/<id>`（见 `src/pages/api/replay/[id].ts`）。合起来查的话，面板就要为一份几小时前
就定死的曲线去等 400KB。

**覆盖率是这条路线的硬约束**，不是技术问题：STRATZ 只为「下载并解析过录像」的对局提供
`playbackData`，而且录像有保留期。实测同一批职业局里，近期的 9012488967 / 9012784253 有
2.1 万个位置点、100+ 个眼位，一周前的 8994002904 / 8987082716 是空数组。所以地图不是
「做了就有」：`didRequestDownload` 为假时不摆注定失败的按钮，为真但上游仍返回空时明说
「STRATZ 没有这场对局的录像数据（只覆盖近期且下载过录像的对局）」。

## 缓存

两个结果都进 `ssrCache` 的内存缓存（运行时上 Workers，没有文件系统）：

- `review:v2:match:<id>`，30 分钟——进行中的对局仍在变，但个人页不需要秒级新鲜度；
- `playback:v2:match:<id>`，60 分钟——已结束的对局不再变化；**没命中录像的也照缓存**，
  否则每来一个访客都替上游跑一次几秒的查询（实测失败路径约 5s）。

键里的 `v2` 是**加字段时升上去的**：这次给解析后的对象补了 `wards` 与选手的 `playerSlot`，
内存缓存里那些旧形状的条目会缺字段，页面只会安静地少一块、不报错。这条规矩在
`docs/data-sources.md` 里以「加头像没升版本」的教训记过一次，改形状就换键。

## 底图从哪来

没有用游戏内地图贴图：Valve / STRATZ / OpenDota 的几条常见小地图路径实测都是 404，
而 redota 那种「把 20MB 版本化地图资源塞进仓库」的做法维护不起。这里画的是**按真实坐标出的示意图**
（`src/lib/dotaMap.ts`），几何全部实测：

- **建筑坐标**：4 场职业对局的 `buildingEvents` 按 npcId 汇总，四场完全一致（只有基地塔差 1–2 格）。
  固化成表之后，每场少拉 500–1000 条建筑事件，而且推塔事件能配上中文名
  （`MatchType.towerDeaths` 只给 npcId，光看数字没人知道是什么）。
- **路数与层数**：按坐标归类（上路沿左边+上边、下路沿下边+右边、中路走对角线），层数按到本方基地
  的距离排。塔本来就长在路边，所以这是几何事实。
- **可行走区域**：两场比赛 4.6 万个真实英雄位置点按方位取 99 分位半径，正方向 63 格、对角 78 格，
  也就是个圆角方形。
- **河与肉山坑**：肉山实际出现过的两处落点——7.33 起他在河两端的两坑之间来回走，所以是两个点。

坐标是 Valve 的 0–255 网格、**y 轴向上**，渲染时翻一次 y（天辉在左下是所有人看小地图的预期）。

## 眼位口径

`playbackData.wardEvents` 是一条条「插下 / 消失」的动作，统计口径有三条，都是实测定的
（`src/lib/wardStats.ts`，`scripts/matchReview.check.ts` 钉住）：

1. **归属靠槽位，不靠位置**：`fromPlayer` 是 Valve 的玩家槽位（天辉 0–4、夜魇 128–132），
   要拿选手自己的 `playerSlot` 去对。试过「插眼时刻离得最近的英雄」，只有 41% 猜对。
2. **到期与被反分开**：`playerDestroyed` 为空 = 没人排掉它。实测印证：空值那批的存活时长中位数
   正好是 360 秒（假眼）与 420 秒（真眼），与游戏里的 6 / 7 分钟一致；有值那批中位数只有
   113–142 秒。把两者并成一个「反眼数」会直接虚高。
3. **两边都记**：被反的眼算「反眼者 +1、插眼者 -1」。只记一边的话，「谁在浪费眼」和
   「谁在排眼」两个问题都答不出来。对照实测一场：天辉插 78（被反 18 + 到期 60）、夜魇插 87
   （被反 33 + 到期 54），十名选手的行加总与两侧合计完全相等。

地图上眼位按**插眼方**着色、按形状分真假眼（圆 = 假眼、菱 = 真眼），SPAWN 到 DESPAWN 之间才画，
所以拖动时间轴看到的正是「那一刻场上亮着的眼」。

## 为什么是独立路由

`/matches/[id]` 是 `getStaticPaths` 预渲染的静态页，几百场对局要在构建期把复盘数据全抓一遍——
构建时间与 `.cache/` 体积一起涨，而多数页从来没人看。这份数据是「谁打开谁付钱」，正好由运行时
那条路承载（与 `/me`、`/party` 的分工一致）。静态赛事页只放一个链接（用页面本来就有的 Valve
比赛 id），不花一分钱。

`/replay/[id]` 同时带 `noindex`：URL 空间是无界的（任何比赛 id 都能渲染一页），对搜索引擎没有
价值，不挡的话等于给爬虫开了个无限抓取、每次还要打一次上游的入口。

## 不做的部分

- 自研 `.dem` 解析器、bzip2 / zstd 解压 worker、IndexedDB 存 50MB 录像 —— 那是 redota 的路
  （1.2 万行、五年、每个 Dota 版本都要救火），代价与站点定位不匹配；
- 单位级 HUD（装备格、技能冷却、血蓝条）、小兵野怪、战争迷雾：`playbackData` 里虽然大多有
  （`abilityUsedEvents` / `inventoryEvents` / `purchaseEvents`…），但一次查询要再翻一倍体积，
  而这个视图要先证明有人看。
