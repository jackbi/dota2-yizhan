# 对局复盘与地图回放

`/replay/<Valve 比赛 id>`：一局打完之后，先回答「这局怎么走成这样的」，再给一张能拖着看的小地图。
入口在赛事对阵页每一局的「复盘与回放」、个人战绩页的对局详情，以及英雄攻略页展开某一局之后的
「这场比赛的对局复盘」。

## 两条数据通道

复盘面板与地图回放**故意分成两次查询**，因为它们的体积差两个数量级、覆盖率也不一样：

| | 查询字段 | 上游体积 / 耗时 | 覆盖范围 |
| --- | --- | --- | --- |
| 对抗明细 + 复盘面板 | 选手行（伤害 / 塔伤 / 治疗 / 装备格）、经济与经验差、逐分钟击杀、胜率模型、塔况位掩码、推塔事件、分路结果、眼位事件 | 约 30KB / 1.4s | 所有被 STRATZ 解析的对局（含一周前的职业局） |
| 地图回放 | `playbackData`：逐秒位置、眼位坐标、肉山、建筑倒塌 | 约 400KB / 2.6s | 只有 STRATZ 下载过录像的对局 |

面板那份跟着页面一起在服务端渲染（无 JS 也能看），地图那份等读者点了「载入英雄轨迹」再取
`/api/replay/<id>`（见 `src/pages/api/replay/[id].ts`）。合起来查的话，面板就要为一份几小时前
就定死的曲线去等 400KB。

**覆盖率是这条路线的硬约束**，不是技术问题：STRATZ 只为「下载并解析过录像」的对局提供
`playbackData`，而且录像有保留期。实测同一批职业局里，近期的 9012488967 / 9012784253 有
2.1 万个位置点、100+ 个眼位，一周前的 8994002904 / 8987082716 是空数组。所以地图不是
「做了就有」：`didRequestDownload` 为假时不摆注定失败的按钮，为真但上游仍返回空时明说
「STRATZ 没有这场对局的录像数据（只覆盖近期且下载过录像的对局）」。

## 缓存

两个结果都进 `ssrCache` 的内存缓存（运行时上 Workers，没有文件系统）：

- `review:v5:match:<id>`，30 分钟——进行中的对局仍在变，但个人页不需要秒级新鲜度；
- `playback:v2:match:<id>`，60 分钟——已结束的对局不再变化；**没命中录像的也照缓存**，
  否则每来一个访客都替上游跑一次几秒的查询（实测失败路径约 5s）。

键里的 `vN` 是**加字段时升上去的**：`v2` 给解析后的对象补了 `wards` 与选手的 `playerSlot`，
`v3` 补了对抗明细的伤害 / 背包 / 中立物品，`v4` 补了选手的号位与分路（AI 赛后分析要用它定位
「谁该做视野、谁该带线」），`v5` 补了购买时间轴（成型件的**时间**，见下面的 AI 赛后分析）。
内存缓存里那些旧形状的条目会缺字段，页面只会安静地少一块、不报错。
这条规矩在 `docs/data-sources.md` 里以「加头像没升版本」的教训记过一次，改形状就换键。

## 底图从哪来

没有用游戏内地图贴图：Valve / STRATZ / OpenDota 的几条常见小地图路径实测都是 404，
而 redota 那种「把 20MB 版本化地图资源塞进仓库」的做法维护不起。这里画的是**按真实坐标出的示意图**
（`src/lib/dotaMap.ts`），几何全部实测：

- **建筑坐标**：4 场职业对局的 `buildingEvents` 按 npcId 汇总，四场完全一致。例外是基地塔：
  npcId 25 / 35 各自对应**一对**塔（实测各有两个落点，如 25 的 `84,86` 与 `82,90`），
  表里按一个点画，所以那一对里的某座倒下时标记会一起打叉。
  固化成表之后，每场少拉 500–1000 条建筑事件，而且推塔事件能配上中文名
  （`MatchType.towerDeaths` 只给 npcId，光看数字没人知道是什么）。
- **路数与层数**：按坐标归类（上路沿左边+上边、下路沿下边+右边、中路走对角线），层数按到本方基地
  的距离排。塔本来就长在路边，所以这是几何事实。
- **可行走区域**：两场比赛 4.6 万个真实英雄位置点按方位取 99 分位半径，正方向 63 格、对角 78 格，
  也就是个圆角方形。
- **河与肉山坑**：肉山实际出现过的两处落点——7.33 起他在河两端的两坑之间来回走，所以是两个点。

坐标是 Valve 的 0–255 网格、**y 轴向上**，渲染时翻一次 y（天辉在左下是所有人看小地图的预期）。

## 对抗明细

十个人的一局账单：英雄 / 玩家、杀 / 死 / 助、NW（占全场最高经济的条）、IMP（按绝对值画条、
正负靠颜色）、LH / DN、GPM / XPM、伤 / 塔 / 奶，以及**保留槽位**的物品栏——6 个主物品 +
3 个背包 + 1 个中立物品，空格子照画，因为「这里空着」本身就是信息。

两处口径容易做错，写在 `src/lib/scoreboard.ts` 并挂进自检：

- **合计行里 GPM / XPM 是相加而不是平均**。这两列看着像"平均值"，其实是**每分钟的量**，
  五个人相加就是"全队每分钟多少钱/多少经验"，与 STRATZ 自己的表一致；按平均值算会得到
  「全队 GPM 只有五六百」这种比单核还低的假数字。
- **IMP 条按绝对值取宽度**。IMP 有正有负，拿带符号的值直接当宽度会画出一个反向的条。

页面把英雄与玩家合成第一列、数字列一律 `whitespace-nowrap`：11 列横排时，折行会把
「12 / 2 / 8」摊成三行，表格高度翻倍而且没法竖着比较。

这份表与个人战绩页的 `MatchScoreboard.astro`（五张选手卡）**故意各写一份**：那边是竖排卡片、
手机上不用横滚，适合"看我这局打得怎么样"；这边是横向对照表，适合"谁在输出、谁在挨打、
谁的钱花在哪"。塞进一个组件只会两边都变形。

## 眼位口径

`playbackData.wardEvents` 是一条条「插下 / 消失」的动作，统计口径有三条，都是实测定的
（`src/lib/wardStats.ts`，`scripts/matchReview.check.ts` 钉住）：

1. **归属靠槽位，不靠位置**：`fromPlayer` 是 Valve 的玩家槽位（天辉 0–4、夜魇 128–132），
   要拿选手自己的 `playerSlot` 去对。试过「插眼时刻离得最近的英雄」，只有 41% 猜对。
2. **到期与被反分开**：`playerDestroyed` 为空 = 没人排掉它。实测印证：空值那批的存活时长中位数
   正好是 360 秒（假眼）与 420 秒（真眼），与游戏里的 6 / 7 分钟一致；有值那批中位数只有
   113–142 秒。把两者并成一个「反眼数」会直接虚高。
3. **两边都记**：被反的眼算「反眼者 +1、插眼者 -1」。只记一边的话，「谁在浪费眼」和
   「谁在排眼」两个问题都答不出来。对照实测一场：天辉插 78（被反 18 + 到期 60）、夜魇插 87
   （被反 33 + 到期 54），十名选手的行加总与两侧合计完全相等。

地图上的眼位画成一只眼睛：**填充色分真假眼**（绿 = 假眼、蓝 = 真眼），**外圈描边分插眼方**
（天辉绿、夜魇红）——「这是真眼还是假眼」和「谁插的」是复盘时最常问的两句，一个点上的颜色与
描边正好各表一边。SPAWN 到 DESPAWN 之间才画，所以拖动时间轴看到的正是「那一刻场上亮着的眼」。

## AI 赛后分析

复盘面板下面挂了一个「AI 赛后分析」：把这一局交给用户自己的模型，讲清胜方靠什么赢、负方输在
哪、负方要怎么打才有机会赢，覆盖对线、节奏与转折、团战与输出、推进与建筑、视野。

**它要回答的是「为什么」，不是把表格念一遍。** 第一版的输出正是后者——把经济曲线和建筑时间轴
复述一遍，读者看完等于又把面板看了一遍。三处改动解决它：

- **提示词禁止复述**：数字只能当证据挂在机制后面，必须先给一次转折点（第几分钟、曲线怎么变、
  最可能的原因），翻盘建议必须是绑在本局弱点上的**可执行动作**；数据不足以归因时要直说
  「看不出是哪一波」，不许用"一般来说"补一个原因。
- **补上能支撑因果的信号**：每座建筑倒塌时**那一刻**的经济 / 经验 / 胜率（把时间轴与曲线对齐）、
  每 10 分钟的净变化（哪一段被拉爆）、两队合计（谁在扛输出）、每名选手的号位与分路，以及
  **成型件的购买时间**（「BKB 26 分钟才有」和「一次都没出」在复盘里是两种打法）。前几项从已有
  数据算；号位与分路、购买时间轴要给上游查询加字段，对应缓存键升 `v4` / `v5`。
- **补上「怎么打的」**：复盘面板只有结果与读数，回答不了「15 分钟后为什么领先」。打法在回放里——
  十个人每一秒在哪。`playbackSummary.ts` 把这 2 万个点聚成几行：什么时候哪一方聚在哪、
  什么时候双方撞在一起、眼布在哪片，外加肉山的位置采样。这份 400KB 的数据**只在读者点
  「生成分析」时才拉**（复用现成的 `/api/replay/<id>`，浏览器缓存一小时），没有录像的对局
  拿不到就少这一段，其余照常。

**边界写死在提示词里**：位置推得出「双方 24 分钟在中路河道撞上」，推不出「谁先手、谁被秒」——
这份数据里没有击杀与施法事件，肉山那份也只是位置采样而不是击杀时间。模型必须在该说「看不出」
的时候说「看不出」，不许用常识补一段过程。

**它只做在这一页，别处只给入口。** 面板要的那套证据（经济与经验曲线、三路结果、伤害与承伤、
推塔时间轴、眼位）只有 `matchReview` 这一份数据有；个人对局页走的是 `stratzPlayer` 的轻量
`MatchDetail`，只有记分板级字段，喂给模型写不出「为什么赢」。个人对局页与赛事对局页的做法与
当初那条约定一致——只放一个指向 `/replay/<id>#ai` 的链接，不各渲染第二份（那两处还省掉了
一次上游查询）。

三层分工，与 `/draft` 的 AI 是同一条边界：

| | 文件 | 干什么 |
| --- | --- | --- |
| 摘要 | `src/lib/matchAnalysis.ts` | 把 `MatchReview` 压成给模型的那份：曲线每 5 分钟采样 + 峰谷 + 最大单分钟变化 + 每 10 分钟净变化，建筑倒塌带上当时的读数，英雄与装备 id 换名字，成型件带上购买时间。**不产生任何新数字。** |
| 打法 | `src/lib/playbackSummary.ts` | 把回放的逐秒位置聚成事件：集结、交战、肉山位置采样、插眼区域。纯函数，浏览器点「生成分析」时才算。 |
| 提示词 | `src/lib/matchAnalysisPrompt.ts` | 拼 system / user 消息，解析回复。不联网。 |
| 请求 | `src/lib/aiChat.ts` | 与 `/draft` 共用的一段：退让顺序、超时、按服务商拼的请求头。 |

一条硬约束写在 system 提示词里、由 `scripts/matchAnalysis.check.ts` 钉住：**数字只能来自给定的
字段，这一局没有胜率预测**——只有数据里出现过 STRATZ 胜率模型的值才可以引用。模型只负责措辞，
解析不过就当这次没结果，界面退回纯数据面板（上面那份表格与曲线不受影响）。

**不点不请求。** 这一页是公开的、URL 空间无界，自动发请求等于替每个到访者花一次他自己的钱。
点了「生成分析」才发（那一刻才去拉回放轨迹），结果按「比赛 id + 地址 + 模型」缓存在本机
（`d2s-match-ai-v3`，最多留 20 场），回访不必重花一次；换了模型，上一份结果立即作废。
**提示词或输入换了也要升这个键**（v2 是加「转折点」、v3 是加打法与出装时间轴）：结构没变、
内容变了同样得作废，否则读者回来看到的是上一版那段话，会以为改动没生效。key 只存在本机、
请求由浏览器直连用户填的地址，服务端不经手——与 `/draft` 一样，这也是这个功能能开源的前提。

摘要内联在页面的 `<script type="application/json" id="match-ai-data">` 里（走 `inlineJson`，
队名里出现 `<` 不会提前闭合脚本元素），浏览器不需要为它再取一次。

## 为什么是独立路由

`/matches/[id]` 是 `getStaticPaths` 预渲染的静态页，几百场对局要在构建期把复盘数据全抓一遍——
构建时间与 `.cache/` 体积一起涨，而多数页从来没人看。这份数据是「谁打开谁付钱」，正好由运行时
那条路承载（与 `/me`、`/party` 的分工一致）。静态赛事页只放一个链接（用页面本来就有的 Valve
比赛 id），不花一分钱。

`/replay/[id]` 同时带 `noindex`：URL 空间是无界的（任何比赛 id 都能渲染一页），对搜索引擎没有
价值，不挡的话等于给爬虫开了个无限抓取、每次还要打一次上游的入口。

页头的「返回」不能写死成一条链接：这条路由有三个入口（赛事对阵页的某一局、个人战绩页的对局
详情、英雄攻略页展开的那一局），写死只能照顾其中一个，而攻略页带 `no-referrer`，服务端看
Referer 也认不出来。所以它是 `history.back()`，`href` 只负责「直接粘贴 URL 打开」时的兜底。
兜底必须指向真实存在的页面：站内只有 `/matches/[id]`，`/matches` 这个索引页从来没有过，
早先写在那儿的一条点下去就是 404。

## 不做的部分

- 自研 `.dem` 解析器、bzip2 / zstd 解压 worker、IndexedDB 存 50MB 录像 —— 那是 redota 的路
  （1.2 万行、五年、每个 Dota 版本都要救火），代价与站点定位不匹配；
- 单位级 HUD（装备格、技能冷却、血蓝条）、小兵野怪、战争迷雾：`playbackData` 里虽然大多有
  （`abilityUsedEvents` / `inventoryEvents` / `purchaseEvents`…），但一次查询要再翻一倍体积，
  而这个视图要先证明有人看。
