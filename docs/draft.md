# 阵容分析（`/draft`）

看比赛的时候手动把双方的 ban/pick 点进来，站点按号位胜率算出几个候选，轮到自己这边时看建议。
也可以让 AI 扮演对面，跟它把一局 BP 打完。页面是静态的，唯一的运行时外部依赖是用户自己的 key。

两种用法共用一套东西：

| 用法 | 谁走对面 | 适合 |
| --- | --- | --- |
| 跟 AI 对打 | AI 自动落子（可关掉改成手动代打） | 自己练 BP |
| 跟直播 | 自己录双方 | 看职业比赛时研究教练怎么选 |

## 人机对战怎么走

轮到我方时，建议面板给三个候选并解释；轮到对面时，用**对面的视角**算一遍候选，再让模型在里面挑一个，
落进 BP 板，旁边留一行"对面刚才禁用了什么、为什么"。这一行在轮到我方之后仍然留着，
因为对手刚动完的那一手正是这一手要参考的信息。

几个刻意的设计：

- **数据先算，模型后挑**。候选、号位、胜率都是本地算的（把 `ourSide` 换成对面即可，
  挑自己缺的位置、禁我们最想要的人），模型只负责在里面选一个并说明。
- **没有 key 也能对打**。模型不可用（没填 key、401、限流、解析失败）时直接取数据里的第一顺位，
  只是它不会解释。对战不会卡在"等 AI"上。
- **自动出招延迟 700 毫秒**，让人先看清"轮到对面了"；这期间自己点英雄池可以抢在它前面录进去，
  定时器醒来会重新判断回合，不会重复落子。
- **替对面写理由要用第二人称**（"你们"指屏幕前的人）。第一版没写这条，模型按自己的视角输出
  "对面拿它打 4 号位……"，出现在"对方禁用了 X"后面时人称是拧的。

## 页面怎么排

左边英雄池、右边 BP 板，都照客户端的样子来：

- **英雄池**：四个属性各占一列并排，每列是一面 45×80 的竖版头像墙（1600 宽下每列六个一行）。
  四组上下堆叠的话一屏只看得到半组，挑人要来回滚。分组标题与属性筛选按钮都带属性图标，
  图标统一放在 `heroApi.ATTRIBUTE_ICON`（英雄页也用同一份，力量/敏捷/智力取官方站点，
  全能官方没有对应图，用 `public/hero-filters/universal.png`）。
- **BP 板**：天辉一列、夜魇一列、中间夹手号，一行一手；框的尺寸按实测写死，
  禁用 55×30、挑选 70×40，两侧朝手号列贴齐。
- **建议面板放在英雄池下面**而不是页面底部：候选卡片点一下就是录入这一手，
  挨着池子用时眼睛和鼠标都不用跑另一栏；顺带把左列撑起来，跟右边的板子差不多齐。

两块面板各自按内容定高、都贴顶，不再强行拉成等高：框的尺寸定死之后，右边本来就比左边高，
拉齐只会在矮的那块里留出一大块空白。

## 为什么 BP 是手动录的

三条路都试过，都不如手点：

| 方案 | 实测结果 |
| --- | --- |
| STRATZ 的实时对局 | 中转不稳：串行打 6 次里有 1 次回 `You cannot use different IP Addresses`（出口是双栈）。放进热路径会变成时不时不工作 |
| OpenDota `/api/live` | 能拿到进行中的比赛与双方英雄，但**只有 pick 没有 ban**，而且观赛时有几分钟延迟 |
| 手动录入 | 准确、零延迟，看直播的人本来就知道对面刚 ban 了什么 |

代价是要点十来下。所以英雄池做得密、点一下就录一手、支持跳过与撤销，候选卡片本身也能点。

## 顺序表从哪来

7.40（2025-12-15）重排了第一和第三禁用阶段的顺序，第二禁用阶段没动。现行 24 手是：

| 阶段 | 手号 | 归属 |
| --- | --- | --- |
| 禁用一 | 1-7 | 先 先 后 后 先 后 后 |
| 挑选一 | 8-9 | 先 后 |
| 禁用二 | 10-12 | 先 先 后 |
| 挑选二 | 13-18 | 后 先 先 后 后 先 |
| 禁用三 | 19-22 | 先 后 先 后 |
| 挑选三 | 23-24 | 先 后 |

双方各 7 禁 5 选。**后选方握着最后一手禁用（第 22 手）和最后一手挑选（第 24 手）**，
先选方拿的是首抢（第 8 手）与一次双选（第 14、15 手）。界面上会把这条直接写出来，
因为它决定要不要留英雄给后面。

右侧的 BP 板照客户端的排法：**天辉一列、夜魇一列、中间夹一列手号，一行一手**（一共 24 行）。
禁用与挑选在**同一列里按手号混排**，禁用格打叉变灰、挑选格是头像。第一版做成了"七个禁用小格
+ 五个选用大格"两段，和客户端对不上，也不方便听解说报"第几手"时找位置。

框的大小也照客户端分开：**挑选框是禁用框整只放大的版本**（宽 92% 对 66%、高 32 对 22），
两侧都朝中间的手号列贴齐，所以放大的只是外侧那一半。禁用格的缩略图只压到 0.68 亮度，
再暗就只剩一团墨、认不出英雄；叉是用 `::after` 画在缩略图上的。每个阶段的起始手
（1、8、10、13、19、23）另留一道缝，禁用段与挑选段一眼能分开。

两个坑记在这里：

1. **别照 Liquipedia 的顺序表**。它只更新了第一禁用阶段，第三阶段还是旧的
   （先-后-后-先），照着写会让第 19 到 22 手的归属全错。现在用的表对着 Valve 的 7.40
   补丁说明写（`datafeed/patchnotes?version=7.40`，站内 `.cache/patches/notes-7.40.json` 就是原文），
   并与三场 2026-09-13 的真实比赛记录逐手核对过。
2. **先选权与阵营是两件事**。先选权落在天辉还是夜魇由选边决定，所以内部一律用
   「先选方 / 后选方」表述，到画界面那一步才映射成两列。

## 建议是怎么算出来的

数据分三层，缺任何一层都能降级：

| 数据 | 来源 | 口径 |
| --- | --- | --- |
| 英雄名、属性、头像 | 官方 datafeed（`heroApi`） | 与英雄页同一份；取不到时退回 OpenDota 的英雄表，属性按全才处理 |
| 号位胜率 | STRATZ `heroStats`（`stratzApi.fetchHeroMeta`） | 超凡入圣及以上、近 7 天、单个号位少于 200 场不计 |
| 英雄对位（克制） | STRATZ `heroStats.matchUp`（`stratzApi.fetchHeroMatchups`） | 同样的高分局口径；只留场次 ≥ 500、胜率偏离五五开 ≥ 4% 的对位，约 1000 对 |
| 职业热度 | OpenDota `/api/heroStats` 的 `pro_*` | 滚动窗口，全英雄合计只有 600 多次出场，只能当旁证，按实数展示 |

对位的两个门槛不是随手定的：300 场的胜率，95% 置信区间就有 ±5.7 个百分点，比要看的偏差还大，
所以场次下限取 500；偏差下限取 4%，只留明显好打或明显难打的对位，接近五五开的不进打分，
免得建议里塞一堆等于没说的依据。接口支持传 `heroIds` 数组，127 个英雄按每批 10 个发 13 次请求，
结果当天缓存，构建期不会每次都跑一遍。

打分对象是**一套阵容在每个号位上能拿到的胜率之和**。已经到手的英雄按最优方式落位
（最多五人，穷举 120 种分配），还没落人的号位按「被打劫之后还能补到谁」折价：把可选英雄
在该号位的胜率降序排，取第 `对手剩余挑选数 + 1` 个，封顶三档；选项不够拿走时按 0 算。

这一步不能省。少了折价，最强的英雄算出来收益是 0（"反正以后也能拿"），候选顺序等于乱序。

**对位（克制）** 作为独立一项叠在号位胜率上：看一个英雄打对面已选的那几个人平均是赢是输，
取偏差的 1.5 倍加进估值（一个 5 个百分点的克制优势，约等于给整套阵容加 0.075）。
系数是拍的，所以每条建议都把对位的原始胜率与覆盖场次写进依据，让人自己判断值不值。
要留意它**不区分分路**：四号位对对面一号位的对位也算在里面，是个粗口径的克制信号。

顺带把「定位」也说明白：建议的号位来自那次最优分配，可能落在英雄的次级位置上；
当它的主位置样本是建议位置的 2 倍以上时，风险里会写出来（"它本周主要打四号位……
放在五号位是次级位置"），免得把一个只有几百场样本的非常规位置当成常规选择。

## 阵容能力与体系对抗

光看胜率会选出"五个都能打、但没人开团也没人推塔"的阵容，所以再加一层**能力维度**：

| 维度 | 数据来源 | 目标值（五人阵容的等级之和） |
| --- | --- | --- |
| 控制 / 爆发 / 先手 / 上高 / 前排 | 官方 datafeed 的 `role_levels`（Valve 自己标的 9 个角色，等级 0-3） | 4 / 4 / 2 / 2 / 2 |
| 清场（清幻象、清兵） | 人工名单 `src/data/heroTraits.ts` | 1；对面是幻象/召唤体系时提到 2 |

打分只算**缺口**：阵容已经有三四个控制时，再选一个控不加分，否则"堆同类"会变成最优解。
每一手能补多少缺口折算成 0 到 1，乘 `COMPOSITION_WEIGHT`（0.12）加进估值，
与号位胜率同尺度（补满一整套缺口约等于某个号位人选好 2.4 个百分点）。界面与提示词都会列出
各维度的现状（如"控制 1/4、清场 0/2"），让"为什么推荐这个"有依据。

**对面是不是幻象/召唤体系**也要认出来：命中 `SUMMON_ILLUSION_NAMES`（幻影长矛手、混沌骑士、
自然先知、陈、育母蜘蛛这些）就把清场目标从 1 提到 2，并在依据里写明是哪一个英雄触发的。

为什么后两类要人写：官方 datafeed 只给 9 个角色标签，没有"幻象/召唤体系"和"清幻象的 AoE"；
STRATZ 的分位统计里倒是有 `stunDuration` / `castDamage` / `cs` 这些字段，**但实测单位对不上**
（沙王三号位场均"眩晕"1.1 秒、陈在单场里"减速 5925 秒"），拿它打分只会得到看着很专业、
实际没意义的结果。所以宁可用一张能被人一眼看懂的名单：按英雄中文名写，构建期与英雄表对账，
对不上的名字写进数据源日志（实测抓到过"先知"应为"自然先知"、"撼地神牛"应为"撼地者"），
不会静默丢掉。版本大改后需要有人过一眼这两张表。

「配合」目前指的是**维度互补**（控制/爆发/先手/上高/前排/清场有没有覆盖到），
不是"某两个英雄同队的胜率"——那需要两人同队的聚合数据，公开源里拿不到可靠样本。

由此推出三种输出：

- 轮到我方挑选：把候选代进我方阵容，看总估值涨多少；
- 轮到我方禁用：把它代进**对面**阵容看对面涨多少（威胁），同时算我们自己拿它的收益，
  自己更想要的降低禁用优先级；
- 界面上的「还缺几号位」，就是估计里还没落人的位置。

**这是启发式，不是胜率预测。** 它只用了一条公开统计，前提是两边水平相当、阵容按位置站好；
页面上也照这个口径写，不出现「胜算 xx%」。

## 模型负责什么

只负责排序和措辞，不负责数据。提示词里给的是算好的候选、号位、胜率、样本量、职业出场与被禁，
并明确三条硬约束：只能从候选里挑、理由里的数字只能来自给定字段、输出必须是 JSON。
回复解析会丢掉候选之外的 `heroId`，解析不过就当这次没有结果，退回纯数据面板。

key 的边界写清楚：存在浏览器 `localStorage`，请求由浏览器直接发给 `api.deepseek.com`
（实测它对本站 origin 放开 CORS），服务端不经手、不落库、不记日志。别人 clone 之后用
自己的 key，作者不承担费用。**浏览器扩展能读到 localStorage 里的 key**，公共电脑上别存，
页面上也这么写。

模型名走 `deepseek-flash` / `deepseek-v4-pro`，请求是 OpenAI 兼容格式；`response_format`
被拒（400）时会去掉该参数重试一次，因为解析层本来就能处理带代码块围栏的回复。

**请求里必须显式关掉思考**（`thinking: { type: 'disabled' }`）。这条不是调优，是不关就没结果：
`deepseek-flash` 默认开着思考，实测同样一条提示词下 900 的 token 上限全被 `reasoning_tokens`
吃掉、`content` 是空的（`finish_reason: length`），把上限提到 4000 也一样空且耗时 21 秒；
关掉之后 1.8 秒返回 288 个 token 的正常 JSON。请求体的组装在 `draftPrompt.ts` 的
`buildChatRequest` 里，`scripts/draftPrompt.check.ts` 盯着这一条别被改掉。

## 文件分工

| 文件 | 职责 |
| --- | --- |
| `src/data/site.ts` | 导航项（`/draft`） |
| `src/pages/draft.astro` | 页面骨架与样式；构建期把数据写成内联 JSON |
| `src/lib/draftOrder.ts` | 24 手顺序表与状态机（纯函数） |
| `src/lib/draftData.ts` | 组装英雄、号位胜率、职业样本 |
| `src/lib/draftScore.ts` | 候选打分与依据生成（纯函数） |
| `src/lib/draftPrompt.ts` | 提示词与回复解析（不联网） |
| `src/scripts/draftBoard.ts` | 客户端：渲染、交互、DeepSeek 调用 |
| `scripts/draftOrder.check.ts` | 顺序表的自检 |
| `scripts/draftScore.check.ts` | 打分层的自检（候选顺序必须说得通） |
| `scripts/draftPrompt.check.ts` | 提示词约束与解析容错的自检 |
| `scripts/draftPage.check.ts` | 页面 id 与脚本对账、显隐手法检查 |

写完页面容易踩的两个坑，都写进了 `draftPage.check.ts`：

1. **标记里的 id 与脚本找的 id 必须对得上。** `getElementById` 找不到只返回 null，
   脚本里的守卫会把整段逻辑静默跳过，表现为「页面上一片空白也不报错」。
2. **别用 `hidden` 类藏东西。** Tailwind 的 utility 层会盖过脚本写的内联 `display`，
   元素永远露不出来；要藏就用内联 `style="display: none"`，并且脚本里必须能找到显示它的代码。

样式那块另有一个坑：**脚本建出来的节点拿不到 Astro 的作用域属性**，所以本页的 `<style>`
必须是 `is:global`，否则英雄格子和 BP 格子全部没有样式（实测症状是格子退回 256px 的原始
图片尺寸、整页被拉成七千多像素高）。

## 验证到哪一步

- `pnpm check`：四个脚本全过（顺序表、打分、提示词、页面结构）。
- `pnpm build`：`/draft` 正常预渲染，内联数据 127 个英雄、约 28 KB，比赛下拉 24 项。
- 浏览器里实测：英雄池 127 个格子、两列各 7 禁 5 选、点英雄会推进手号、撤销/跳过/清空正常、
  切换先选权后两列归属整体镜像、刷新后进度从 localStorage 恢复、候选卡片点了就是录一手。
- 接口层：用无效 key 打真实的 `api.deepseek.com`，`/models` 与 `chat/completions` 都返回 401，
  页面上分别显示「失败：HTTP 401」与「key 无效或已过期」；请求体与回复渲染用打桩验证过。
- **没验的部分**：真实模型调用没跑（需要真 key，会花钱），所以模型输出质量只靠提示词约束与
  解析容错保证，实际效果要你自己拿一场比赛试试。

## 已知取舍

- 比赛下拉是**构建期快照**，跟站内赛程页一样不会自己刷新；选不到就手输队名，留空也能用。
- 职业样本太小，页面上只按实数展示出场与被禁次数，不换算成百分比。
- 有对位数据之后，「禁用」建议会一起看"对面拿走它会不会正好克我们的人"；但**同队协同**
  （谁和谁搭档强）还没有：公开源里没有现成的两人同队胜率，要用 OpenDota 的 SQL 自己聚合，
  而那边 30 天内解析过的对局里，单个对位最多只有几十场，纯噪声。
- 对位是高分路人局的口径，不区分分路，也不是"这局谁在线上遇到谁"。
- 跳过的出手不计入阵容，因此中途开始跟的时候，阵容估值只反映你录进来的部分。
- 号位胜率是高分路人局，不是职业赛场；职业赛场的打法差异（换线、双辅助游走）它看不出来。
