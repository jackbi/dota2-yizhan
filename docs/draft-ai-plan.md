# 阵容分析 AI 配置改造清单

> 状态：**已实施**（阶段 1、2、3 都完成）。写于 2026-09-28，同一天落地。
> 涉及代码：`src/lib/draftPrompt.ts`、`src/scripts/draftBoard.ts`、`src/pages/draft.astro`。
>
> 实施结果与下面这份计划的差异见文末「实施结果」，设计细节以 `docs/draft.md` 的
> 「模型负责什么」「配置住在哪」两节为准。

## 为什么要做

两个各自独立的问题，顺路一起解决：

1. **AI 配置和 BP 台挤在一起，将来没法复用。** key 与模型名写在 `/draft` 页面里，配置存在 BP 进度同一个 localStorage 对象里；别的页面要用 AI 就得把这套读写逻辑再抄一遍。
2. **界面上的 AI 标签与事实不符。** 「对面交给 AI」默认是开的，但没配 key 时对面走的是本地启发式，台头却写着「夜魇（AI）禁用」。用户以为模型在走，其实没有。

顺带记一条调研结论：**阵容分析本身不依赖 AI**，所以「没配 AI 就不能用」是个误解，本次改造也不打算引入任何第三方分析库。

## 现状事实

### 没配 AI 时，三块功能各自的实际表现

| 功能 | 由谁算 | 没配 AI 时 |
| --- | --- | --- |
| 建议面板 | `src/lib/draftScore.ts`（45KB 纯函数：号位最佳分配、对位权重、阵容结构分与红线、时间曲线） | **完整可用**。候选卡、依据、风险、阵容结构、号位预测全都照常渲染，只是摘要不加「AI：」那句 |
| 复盘胜率 | `src/lib/draftVerdict.ts`（号位偏差 + 对位偏差、五维对比、分路对位） | **完整可用**。数字全在，只少一段文字解释 |
| 对手出招 | `src/scripts/draftBoard.ts` 的 `playOpponentMove` | **照常走**，退回候选第一顺位 + 本地依据；问题只在标签 |

模型的介入点很浅：在已经排好序的候选里挑一个、写一段措辞（`renderAdvice` 第 933 行）。它不参与任何数字。

### AI 的调用面

| 位置 | 用途 |
| --- | --- |
| `src/lib/draftPrompt.ts:40` | 端点常量 |
| `src/scripts/draftBoard.ts:827` | 复盘文字 |
| `src/scripts/draftBoard.ts:1107` | 对手出招 |
| `src/scripts/draftBoard.ts:1356` | 连接测试（打 `/models`，地址写死） |
| `src/scripts/draftBoard.ts:1400` | 建议解释 |

### 两个硬约束

- **存储**：`STORE_KEY = 'd2s-draft-v1'` 一个对象里同时装着 key、模型名、aiSide 与全部 BP 进度；`save()` 每次整块回写（`draftBoard.ts:223`）。所以设置页一旦去写配置，就会把 BP 进度一起写回去，多标签页下会互相覆盖。
- **自检**：`scripts/draftPage.check.ts` 要求脚本里 `element('id')` 找的每个 id 都必须在 `draft.astro` 里存在。搬走输入框必须同步删掉脚本里的引用，否则 `pnpm check` 直接失败。

## 调研：有没有现成的开源阵容分析库

2026-09-28 在 GitHub 上按 draft / recommendation / win prediction / synergy 等关键词查过，结论是**没有能直接拿来用的**：

| 项目 | 星数 | 状态 | 性质 |
| --- | --- | --- | --- |
| odota/core | 1629★ | 活跃 | OpenDota 数据平台本体，是数据层而非分析引擎（本站已在用） |
| mdiller/dotabase | 61★ | 活跃 | 游戏文件导成 SQLite（英雄/技能/物品），不含分析 |
| vpus/dota2-win-rate-prediction-v1 | 27★ | 2018 停更 | 胜率预测模型，版本数据已过期 |
| dojeon-ai/DraftRec | 18★ | 2023 | 论文代码，研究原型，需自行训练 |
| dota2-draft-analysis / DraftML / LatentDraft / dota2_ai_drafter 等 | 0–8★ | 多为 2016–2022 | 学生作业与个人玩具，无可调用的包或 API |

原因：BP 分析的价值绑在当期版本的对局样本上，数据一过期库就废。数据层开源、分析层闭门——商业站各做各的，学术产出论文多于代码。这与本站 `docs/draft.md` 里已经记录过的结论一致（同队协同样本在公开源里不够用）。

**所以本次不引入任何第三方分析库**，缺的那点「人话」用本地模板补，见阶段 1.3 / 1.4。

## 阶段 0 · 开工前要定的三件事

| 决策 | 选项 | 建议 |
| --- | --- | --- |
| 配置存哪 | 只存本机 localStorage / 做成账号级存服务端 | **只存本机**。账号级会推翻 `docs/draft.md:330` 那条公开承诺（key 不经服务端、作者不担费用），是另一个量级的事 |
| 路由 | `/settings` / `/draft/settings` | **`/settings`**，中性，将来 AI 用到别处能复用 |
| 未配置时「对面交给 AI」 | 默认关掉 + 提示 / 开着但把标签改成「（本地）」 | **默认关掉**。该开关现在默认开，首次访问的用户会看到「（AI）」跑了半天其实没接模型 |

## 阶段 1 · 修标签 + 补本地解释

**不改配置的位置与存储后端**，只做增量；独立上线，就算后面决定不搬设置页也不白做。约 1 天。

### 1.1 收敛配置读写（`refactor`）

新增 `src/lib/aiConfig.ts`：配置形状、读、写、以及三态判定（未配置 / 上次失败 / 正常）。
后端**先指回现有的 `d2s-draft-v1` 字段**，阶段 2 再换成独立 key——先把「哪些地方要读配置」收敛掉，阶段 2 的 diff 才不会散在四处。

### 1.2 修掉「标着 AI 实际不是」（`fix`）

- `syncAiBlock`（`draftBoard.ts:1000`）：台头那句 `（AI）` 按三态走，未配置时不再声称是 AI。
- `playOpponentMove`（`draftBoard.ts:1053`）：落子说明注明当前依据，而不是让人以为模型走过。
- `explainWithModel`（`draftBoard.ts:1365`）与 `analyzeVerdict`（`draftBoard.ts:810`）：没配置时给状态文案 + 去配置入口，替掉现在 `focus()` 并把页面滚到输入框的那段（输入框一搬走这段就失效了）。
- 状态文案去 DeepSeek 化：`DeepSeek 余额不足` → `余额不足`，`先在下面填 DeepSeek key` 改口径（`draftBoard.ts:818`、`:1370`、`:1415`，`draft.astro:14`、`:62`、`:291`）。

### 1.3 无模型时的模板解释（`feat`）

把 `candidate.reasons[]`、`risk`、`composition.text`、`lineup` 拼成一段连贯的中文，作为没配 AI 时的默认解释层。
落在纯函数里（新 `src/lib/draftNarrative.ts` 或并入 `draftScore.ts`），可被自检脚本直接调用。
它有个模型给不了的好处：数字全部来自代码，不可能编。

### 1.4 对手出招的措辞模板化（`feat`）

现在 `why` 只有一句「按号位胜率与剩余手数判断」。改成按实际依据拼：对面熟手、补哪个号位的缺口、还剩几手。仍是本地规则，不调模型。

### 1.5 自检

新增 `scripts/aiConfig.check.ts`（三态判定 + 读写往返）；模板解释的文案断言并入 `scripts/draftPrompt.check.ts` 或新建；若动了页面 id，同步 `scripts/draftPage.check.ts`。

## 阶段 2 · 设置页与配置搬家

约 1–1.5 天。

### 2.1 存储拆 key + 迁移（`refactor`，单独提交）

配置挪到独立的 `d2s-ai-v1`，**带一次性迁移**：老用户的 key 现在躺在 `d2s-draft-v1` 里，必须自动搬过去，不能让人重填。拆开之后，设置页写配置不再覆盖 BP 进度。

### 2.2 新增配置页（`feat`）

`src/pages/settings.astro` + `src/scripts/settingsForm.ts`，字段：API 地址、key、模型名、测试连接、清除、保存。
这版先把地址与模型名做成可填（能接任何 OpenAI 兼容服务），**不做**提供商预设，留给阶段 3。

### 2.3 连接测试结果落库

存 `lastCheckedAt` / `lastOk`，BP 台才能直接显示「已配但上次失败」，而不是每次都要重测。
`testConnection`（`draftBoard.ts:1352`）现在打的是写死的 `api.deepseek.com/models`，一并改成读配置里的地址。

### 2.4 BP 台瘦身

`draft.astro` 的设置区缩成一行状态 + 去配置链接；`draftBoard.ts` 删掉 `draft-key` / `draft-model` / `draft-test` / `draft-clear` 四处 `element()` 引用（`draftBoard.ts:195`、`:197`、`:1315`、`:1320`），并同步删页面元素，否则 1.5 里那条 id 对账会失败。

### 2.5 入口

BP 台一行链接、`/me` 一个入口；**不加进主导航 NAV**（已经有 10 项了）。

### 2.6 自检

新增 `scripts/settingsPage.check.ts`，照 `draftPage.check.ts` 的写法做页面 id 与脚本 id 对账。

### 2.7 sitemap（待定）

`/settings` 是个人配置页，没有收录价值。可以照 `/me/*` 的做法在 `astro.config.mjs` 的 sitemap filter 里排除，也可以先不管。

## 阶段 3 · 提供商预设（可选，之后单独评估）

一张静态表：名称 + 默认地址 + 常见模型 + 参数差异。参数差异才是这步的真正成本：

- `thinking: { type: 'disabled' }` 是 DeepSeek 专有，换成 OpenAI 会被严格校验判 400，必须按提供商条件注入（`draftPrompt.ts:450`，`docs/draft.md` 里写明这条不是调优，是不关就没结果）；
- `max_tokens` 在部分新模型上只认 `max_completion_tokens`；
- `response_format` 不是人人支持——现有的「400 就去掉该参数重试一次」正好复用；
- **CORS**：本站是浏览器直连，能否只改前端取决于提供商是否放开 CORS。不放开就只能走服务端代理，那会推翻「站点不经手 key」的前提，不属本次范围。

## 明确不做

- 账号级 / 服务端存 key（与公开承诺冲突，另立项）
- 服务端代理转发 AI 请求
- 自己训练胜率预测模型
- 聚合同队协同数据（公开源样本不足，见 `docs/draft.md` 已记录的结论）
- 引入第三方开源阵容分析库（调研结论：没有可用项）

## 验证方式

1. `pnpm check` 全过（现有 29 个自检脚本 + 本次新增）。
2. `pnpm build` 正常。
3. 浏览器手测：
   - 未配置时，BP 台台头 / 建议面板 / 复盘三处的提示是否说得清，且不再声称是 AI；
   - 配置后三处恢复正常；
   - key 无效（401）时三态显示是否正确；
   - 老 localStorage 数据迁移后 key 是否还在（阶段 2 必测）；
   - 模板解释在没配置时的可读性。

阶段 1、2 都不动服务端，也不改请求体结构。

## 风险与边界

- **迁移不能丢 key**，这是唯一有数据风险的一步，先在真浏览器上拿旧数据试一遍。
- **阶段 2 之后 BP 台不再有 key 输入框**，改 key 必须去设置页；「去配置」的跳转路径要够显眼，否则用户会以为功能坏了。
- `draftPage.check.ts` 的 id 对账是硬约束，页面与脚本必须同一提交里改。

## 实施结果

落地时与上面这份计划有三处不同，都是有意为之：

1. **阶段 1 与阶段 2 一起做了**，所以计划里那个「`aiConfig` 先指向旧存储、阶段 2 再换后端」的
   过渡步骤没有做——那会白白多写一版马上要删的代码。`aiConfig.ts` 直接落在最终形态上，
   迁移逻辑本来就要读旧键，顺手就位。
2. **`/me` 入口改放页脚。** `/me` 是 Steam 登录后的战绩面板，把一个「浏览器的 AI 配置」
   塞进战绩页既不合语境也帮不到匿名访客。改成页脚一个链接（不进主导航，理由写在
   `Layout.astro` 的注释里）。
3. **多做了一步本该属于阶段 3 的参数适配**：`thinking: { type: 'disabled' }` 改成只在
   DeepSeek 域名下发。不做这一步的话，地址一旦填成别家，请求会被 400 拒掉，用户只会看到
   「连不上」——把一个能用的功能变成陷阱，不如现在就把这条判断加上。

阶段 3（服务商预设）后来也做了，与计划里的写法有两处不同：

1. **计划里写的是「常见模型」列在表里，落地改成了「向服务商要」**。模型名变得比 API 快，
   内置一份清单过期了只会让人以为功能坏了；现在设置页有个「拉取模型列表」，直接打
   `<地址>/models` 把结果填进下拉，表里只留一两个建议值兜底。
2. **表里的地址与跨域结论全部实测过**，不是照抄文档：用无效 key 打 `/models` 看路径是否存在，
   发 `OPTIONS` 预检看放不放行跨域。Anthropic 那条就是这么发现的——不带它那个专用头，
   预检直接 400 且没有 CORS 头，浏览器根本发不出去。结论表见 `docs/draft.md` 的「服务商预设」。

Chrome 内置模型（Gemini Nano）**没有纳入**：它没有 HTTP 端点，与本站「填一个地址直接发请求」
的结构接不上，想接得另写一条调用路径。这条限制写在 `lib/aiProviders.ts` 的注释里。

那两步实测后来也做成了脚本（`scripts/aiProviders.probe.ts`，`pnpm probe:providers`）：它探的
就是预设表本身，加新服务商时不用再手工 curl。跑起来带出的两个坑都写进了脚本注释——Node 的
`fetch` 默认不走代理环境变量（需要代理的服务商会被误报成「连不上」），以及边缘节点偶尔会把
探测请求当异常流量（所以第一次不正常就重试一次）。它联网，所以不进 `pnpm check`。
